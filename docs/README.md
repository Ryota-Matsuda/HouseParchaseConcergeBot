# HouseParchaseConcergeBot

住宅購入向けの **個人用コンシェルジュBot** です。  
候補条件に合う新着物件を定期取得し、AI が短い要約と優先度を付けて LINE に通知することを目指します。

> この README は、2〜3 日ぶりに作業を再開するときに **短時間で設計を思い出すための設計メモ** として使うことを目的にしています。

---

## まず最初に読む要約

- **何を作るか**: 新着物件監視 + 厳密条件フィルタ + AI要約/優先度付け + LINE通知
- **何はまだやらないか**: 高度なUI、フル自律エージェント、外部調査自動化、自動問い合わせ
- **MVPの核**: 取得 / 正規化 / フィルタ / 重複排除 / AIスコアリング / 通知
- **設計思想**: ルールで決められることはコードで、曖昧さの処理だけ AI に任せる
- **最初の実装順**: 開発基盤 → API雛形 → ドメインモデル → DB → Rule Engine → SourceAdapter → 通知

---

## 背景と目的

住宅購入候補の情報収集は、複数の物件サイトを継続的に見て新着を追う必要があり、手作業だと見落としや通知疲れが起きやすいです。  
このプロジェクトでは、対象条件に合う物件だけを機械的に拾い、その上で AI が「なぜ気になる候補なのか」を短く説明することで、意思決定の初速を上げます。

個人利用の学習プロジェクトとして始め、将来的には以下を見据えます。

- フィードバックを使った順位改善
- データソース差し替え
- 事業利用を見据えた拡張可能な構成

## 想定ユーザー像と前提条件

現時点の前提条件は以下です。

- 27歳
- まだ子どもはいないが、2年以内に出産を検討
- 候補地: 戸塚 / 藤沢 / 茅ケ崎 / 辻堂 / あざみ野 / 中央林間
- 駅徒歩15分以内
- 注文住宅 / 分譲マンション / 分譲住宅を対象
- 通知先は LINE
- 個人利用前提

## メンタルモデル（ドメインモデルの全体像）

![住宅購入コンシェルジュBot メンタルモデル](./Images/mentalmodel.png)

### ざっくり理解

このシステムは、以下の流れで考えると追いやすいです。

1. **SearchProfile** が「どんな物件を探したいか」を表す
2. **SourceAdapter** が物件ソースからデータを取得する
3. 取得した生データを **RawListing** として保存する
4. それを **Listing** という共通形式に正規化する
5. **Rule Engine** が厳密条件でふるいにかける
6. 通過した物件に対して AI が **MatchResult** を作る
7. **NotificationService** が LINE に通知する

### ドメイン用語の最小セット

- **SearchProfile**: 検索条件セット
- **RawListing**: ソースから取得した生データ
- **Listing**: 共通形式に正規化した物件データ
- **MatchResult**: AI要約・優先度・理由を持つ評価結果
- **Notification**: 送信した通知の記録
- **Feedback**: ユーザーが後で返す「興味あり / 見送り」などの反応

## 要件概要

### MVPで必ずやること（機能要件）

1. 物件ソースから新着情報を定期取得する
2. 共通フォーマットへ正規化する
3. エリア / 徒歩 / 種別で厳密フィルタする
4. 重複排除する
5. AI が短い要約と優先度を付ける
6. LINE に通知する

### MVPではやらないこと

- 高機能な管理UI
- 周辺施設や学区などの外部調査自動化
- 自律的なエージェント行動
- 自動で問い合わせや内見予約をする機能
- 高度なレコメンド学習

### MVP+ 以降でやりたいこと

- LINE 上でのフィードバック入力
- フィードバックを使った順位調整
- 日次/週次ダイジェスト
- データソース追加
- 条件セット複数化
- 将来の事業利用を見据えたソース差し替え

## 要件詳細

### 1. 物件取得

- 少なくとも 1 つの物件ソースから一覧取得できる
- 一定間隔で定期実行できる
- 取得失敗時にログが残る

### 2. 正規化

最低限、以下の項目を `Listing` に持たせる。

- source
- source_listing_id
- title
- url
- area_name
- station_name
- walk_minutes
- property_type
- price_text
- layout
- size_text
- description

### 3. 厳密フィルタ

以下をまずは決定的ロジックで判定する。

- 候補地に含まれるか
- 駅徒歩 15 分以内か
- 対象種別か

### 4. 重複排除

- `source + source_listing_id` を基本キーにする
- 初回取得時は保存のみで通知しない運用も可能にする
- 同一物件の再通知を防ぐ

### 5. AIスコアリング

AI が担当するのは以下。

- 80〜120文字程度の要約
- 優先度（high / medium / low）
- 良い点
- 注意点
- なぜ候補に合いそうかの短い説明

### 6. 通知

LINE 通知には最低限以下を含める。

- タイトル
- エリア
- 駅 / 徒歩
- 価格
- 種別
- AI要約
- 優先度
- URL

1. わかりやすさ
2. 拡張性
3. 運用のしやすさ
4. 性能最適化

## 設計方針

### 1. ルール中心 + AI補助

AI は便利ですが、毎回 AI に全部判断させる必要はありません。  
条件一致・重複判定・保存・通知などの **決められる処理はコードで** 実装し、  
「説明」「要約」「優先度の補助判断」のような **曖昧さを含む部分だけ AI に任せる** 方針です。

### 2. 依存方向を単純に保つ

- Source ごとの差異は Adapter に閉じ込める
- ドメインモデルはできるだけ共通化する
- 通知手段は Service / Notifier で差し替え可能にする

### 3. MVPでは一番細い道を通る

最初から全部作らず、以下の順で一筆書きできる状態を作る。

`取得 → 正規化 → フィルタ → 重複排除 → AI要約 → LINE通知`

## モジュール構成

```text
app/
  api/
    webhook.py
    health.py
  batch/
    run_watch_job.py
  domain/
    models/
    services/
  infra/
    db/
    source_adapters/
    llm/
    notifier/
  schemas/
  config.py
```

### 各モジュールの役割

- **api/**: FastAPI の入口。Webhook や health check を置く
- **batch/**: 定期実行ジョブの起点を置く
- **domain/models/**: Listing などの中核概念を定義する
- **domain/services/**: Rule Engine や NotificationService を置く
- **infra/db/**: SQLAlchemy モデルや Repository を置く
- **infra/source_adapters/**: ソースごとの取得処理を置く
- **infra/llm/**: AIスコアリング処理を置く
- **infra/notifier/**: LINE通知処理を置く
- **schemas/**: Pydantic スキーマを置く
- **config.py**: 環境変数や設定管理

## 処理フロー

### Watch Job の基本フロー

1. スケジューラがジョブを起動する
2. SourceAdapter が物件一覧を取得する
3. RawListing を保存する
4. Listing に正規化する
5. Rule Engine が条件一致を判定する
6. 重複排除する
7. AI が MatchResult を生成する
8. NotificationService が LINE 通知する
9. 実行結果を記録する

## データモデルの考え方

### SearchProfile
「何を探すか」を表す条件セット。  
候補地、徒歩上限、対象種別などを持つ。

### RawListing
各ソース固有の生データ。  
将来、Normalizer を見直したくなったときのために残す。

### Listing
ソース差異を吸収した共通物件モデル。  
アプリ全体では基本的にこの形を使う。

### MatchResult
AI が作る評価結果。  
通知文を作る前段階の「意味づけ」データ。

### Notification
何をいつ送ったかの履歴。  
再通知防止や後での確認に使う。

### Feedback
将来の順位改善に使う。  
MVPでは保存枠だけを先に作る。
